**Estado:** API y frontend desplegados en Railway. La API pública `https://libroya-api-production.up.railway.app` respondió `{"status":"ok"}` en `/health` y cinco libros en `/api/books`. El primer arranque de API falló por acceso de red de Atlas; después de activar la entrada temporal `0.0.0.0/0`, `railway redeploy --service libroya-api` dejó `libroya-api` online. La web recibió `NEXT_PUBLIC_API_URL` antes de compilarse; `railway up --service libroya-web` compiló Next.js 16.4.6, arrancó en el puerto 8080 y pasó su healthcheck. El dominio `https://libroya-web-production.up.railway.app` fue creado para el puerto 8080. La captura `e37.png` muestra los cinco libros con portadas después de configurar `CLIENT_ORIGIN`. TestSprite aprobó T01, T04 y T05 localmente (3/3) y en el dominio público (3/3). PayPal Sandbox aceptó las credenciales mediante OAuth, capturó una compra digital de prueba y LibroYa la reconcilió, entregó y permitió descargar el archivo. WebSocket cuenta con una prueba automática local.

## Preparación local de Atlas

1. Crear en Atlas el proyecto `LibroYa`, el clúster gratuito `LibroYa-dev`, la base `libroya`, la colección `books` y el usuario de aplicación `libroya_app` con `readWrite` limitado a `libroya`.
2. En **Connect → Drivers → Node.js**, copiar la cadena de conexión. Desde la raíz del proyecto, ejecutar `powershell -ExecutionPolicy Bypass -File .\scripts\configurar-atlas.ps1`; pegar la cadena en el primer aviso oculto y escribir la contraseña de `libroya_app` en el segundo. El script extrae el host, codifica la contraseña para URI y guarda la conexión únicamente en `server/.env`. No incluirla en Git, capturas ni conversaciones.
3. Ejecutar `npm.cmd run setup:atlas` para instalar Mongoose y actualizar `server/package.json` y `package-lock.json`. Después ejecutar `npm.cmd run seed -w server`, iniciar la API y comprobar `/health` y `/api/books`.
4. Volver a Atlas Data Explorer, actualizar `libroya > books` y comprobar que aparecen cinco documentos. Registrar una compra de prueba y revisar las colecciones `users` y `orders` sin exponer datos personales.

Si `seed` falla con `querySrv ECONNREFUSED`, el DNS local no está resolviendo los registros SRV del URI `mongodb+srv://`. En **Connect → Drivers → Node.js**, activar **Legacy URI String** para obtener una cadena estándar `mongodb://` con los nodos y sus opciones. Ejecutar de nuevo `scripts/configurar-atlas.ps1` con esa cadena; el script conserva las opciones de conexión, añade TLS si hace falta y vuelve a guardar la URI privada. Reintentar `seed`. [MongoDB recomienda la cadena no SRV para este error](https://www.mongodb.com/docs/atlas/troubleshoot-connection/).

Si `MONGODB_URI` está vacía, la aplicación usa SQLite local. La carga inicial, el catálogo, pedidos cancelados, una captura PayPal Sandbox reconciliada y la descarga digital se comprobaron contra Atlas.

## Preparación de PayPal Sandbox

1. Iniciar sesión en [PayPal Developer Dashboard](https://developer.paypal.com/dashboard/). En **Apps & Credentials**, usar **Sandbox** y crear una aplicación Merchant llamada `LibroYa-Sandbox` asociada a una cuenta Business Sandbox. PayPal proporciona cuentas Sandbox Personal (comprador) y Business (vendedor) de forma predeterminada.
2. Desde la raíz del proyecto ejecutar `powershell -ExecutionPolicy Bypass -File .\scripts\configurar-paypal-completo.ps1`. El primer intento con `LibroYa-Sandbox` guardó solo un carácter por credencial y PayPal respondió HTTP 401. El script corregido pide copiar cada valor con el icono del panel y presionar Enter sin pegarlo en la terminal; lee y borra el portapapeles, exige al menos 20 caracteres y valida OAuth antes de enviar nuevos valores a `libroya-api`. El segundo intento pasó OAuth y envió las variables corregidas a Railway. No compartir credenciales por chat ni incluirlas en capturas. Si se usa también la API local, reiniciarla para aplicar las variables.
3. El script completo ejecuta `node scripts/verificar-paypal-sandbox.mjs` antes de enviar las variables. Solo valida las credenciales con OAuth y no crea pagos. Desde el entorno del asistente, la red impidió realizar esta comprobación; el segundo intento desde el equipo del estudiante recibió un token OAuth válido.
4. Registrar un cliente ficticio en LibroYa, añadir un libro y aprobar la compra con la cuenta **Personal Sandbox**. Confirmar en `orders` y `payments` que el pedido está capturado; para un eBook, comprobar la descarga autenticada. Usar un segundo pedido para probar cancelación de aprobación.

[PayPal explica las cuentas de comprador y vendedor Sandbox](https://developer.paypal.com/sandbox-testing/accounts).

## Configuración prevista en Railway, sin Git

Railway permite [subir y desplegar archivos locales con `railway up`](https://docs.railway.com/cli/up). No hace falta crear un repositorio para esta fase. El proyecto incluye `.railwayignore` para omitir credenciales locales, bases SQLite, evidencias, documentos y archivos de prueba. La CLI omite también `.git` y `node_modules`.

1. Crear el proyecto Railway `LibroYa` y dos servicios vacíos: `libroya-api` y `libroya-web`. Vincular la CLI con `railway link`. El [plan Free](https://docs.railway.com/pricing/free-plan) no exige tarjeta y ofrece un crédito mensual limitado; las cuentas nuevas reciben un crédito de prueba por 30 días. Revisar el consumo al desplegar, especialmente porque la API mantiene una conexión con Atlas.
2. Mantener la raíz `/` del monorepo como directorio de construcción para ambos servicios, porque `package.json` y `package-lock.json` contienen los workspaces. El archivo `.node-version` fija Node.js 24 para [Railpack](https://railpack.com/languages/node). En `libroya-api`, dejar Railpack como builder, fijar la compilación en `npm run test -w server`, el inicio en `npm run seed -w server && npm run start -w server` y el healthcheck en `/health`. En `libroya-web`, configurar compilación `npm run build -w web` e inicio `npm run start -w web`. Los comandos de servicios se ajustan en Settings o con [`railway environment edit`](https://docs.railway.com/deployments/monorepo). No usar `railway.json`: la [configuración de servicio en código está deprecada](https://docs.railway.com/config-as-code) y los servicios nuevos ya no pueden adoptarla.
3. Antes del primer despliegue de la API, ejecutar `node scripts/configurar-railway-api.mjs` desde la raíz del proyecto. El script lee de `server/.env` `MONGODB_URI`, `STAFF_EMAIL` y `STAFF_PASSWORD`, genera un `JWT_SECRET` nuevo y envía estos valores junto con `NODE_ENV=production` por stdin a `libroya-api`, sin imprimirlos ni incluirlos en la línea de comandos. Usa `--skip-deploys` para agrupar cambios. Comprobar en la pestaña Variables que aparezcan los cinco nombres y aplicar los cambios pendientes. Railway proporciona `PORT`. Configurar `CLIENT_ORIGIN=https://<dominio-web>` después de conocer el dominio de la web. `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_API_BASE=https://api-m.sandbox.paypal.com` y `PAYPAL_CURRENCY=USD` ya se enviaron con los valores corregidos. Las credenciales no se incluyen en capturas ni conversaciones.
4. Configurar la variable de la web `NEXT_PUBLIC_API_URL=https://<dominio-api>` después de conocer el dominio de la API y **antes de compilar la web**. Next.js la incluye en el paquete del navegador; nunca usar ese prefijo para secretos.
5. Desde la raíz de este proyecto, subir primero la API con `railway up --service libroya-api`. El primer intento compiló y aprobó 7/7 pruebas, pero Atlas rechazó la conexión desde Railway y el healthcheck falló. Railway solo ofrece IP saliente estática en Pro; para este laboratorio en Free, agregar en Atlas una entrada **temporal de una semana** para `0.0.0.0/0`, con comentario `Railway LibroYa laboratorio`, mantener el usuario `libroya_app` limitado a `libroya` y una contraseña fuerte. Esta regla abre el acceso de red desde cualquier IP durante su vigencia; eliminarla cuando termine la demostración o sustituirla por IPs salientes estáticas si cambia de plan. Cuando la entrada esté activa, ejecutar `railway redeploy --service libroya-api` para reintentar la imagen ya subida en el entorno vinculado `production`. Después de que escuche en el puerto `PORT` suministrado por Railway, generar su dominio HTTPS en Settings → Networking; [Railway detecta el puerto de un servicio desplegado](https://docs.railway.com/networking/domains/working-with-domains). `e32.png` mostró que intentarlo antes pide un puerto manual. Comprobar `/health` y `/api/books`. [Atlas documenta las entradas temporales](https://www.mongodb.com/docs/atlas/security/ip-access-list/) y [Railway limita las IPs salientes estáticas al plan Pro](https://docs.railway.com/networking/static-outbound-ips).
6. Configurar `NEXT_PUBLIC_API_URL` en `libroya-web` con el dominio HTTPS de la API **antes de compilar** y subir la web con `railway up --service libroya-web`. Generar su dominio después de que escuche en `PORT`. Establecer `CLIENT_ORIGIN` de la API con el dominio HTTPS de la web y volver a desplegar la API. Comprobar registro, catálogo, historial, tablero y reconexión WebSocket (`wss://`). `railway up` no crea un dominio público por sí solo.
7. Verificar el despliegue de PayPal Sandbox y probar un pago con cuenta Personal Sandbox. La URL pública ya existe; TestSprite Free solo permite un entorno guardado, por lo que las pruebas públicas se ejecutaron con `--target-url`. La primera fase local se documenta en [plan TestSprite](PLAN_TESTSPRITE.md).
