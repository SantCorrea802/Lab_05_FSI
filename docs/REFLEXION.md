# Reflexión individual sobre el desarrollo con IA

La IA generativa se usó para proponer la estructura del proyecto, la interfaz, la API, las reglas de negocio, las pruebas y las portadas de cinco libros ficticios. El resultado se adaptó a la actividad de la guía: una tienda de libros electrónicos con catálogo, stock y envíos. Para representar los envíos también se incluyeron libros impresos. Las propuestas se revisaron frente al PRD y al funcionamiento real antes de incorporarlas.

La verificación no se limitó al código generado. Se ejecutaron once pruebas automáticas del servidor, se compiló la web y se probaron en TestSprite los doce casos previstos: once aprobaron en la web pública y uno quedó bloqueado por límites de automatización. El catálogo, los filtros y la bolsa también aprobaron localmente. La prueba de cancelación detectó un botón de verificación indebido en un pedido cancelado; se corrigió y aprobó al repetirse. La validación detectó el mensaje poco claro «Dirección inválido»; se corrigió en la web y la API y también aprobó al repetirse. El primer caso de permisos quedó bloqueado porque el navegador del agente no hizo llamadas HTTP; se revisó para comprobar solo la interfaz y aprobó, mientras que la API pública se verificó de forma directa junto con precio, propiedad de pedidos, validación y descargas. T06 falló inicialmente por pedir datos que PayPal Sandbox no mostraba antes del ingreso; se revisó para comprobar el total visible en la bolsa y el pedido, y aprobó. T07 logró confirmar una compra digital Sandbox y mostrarla entregada, pero el navegador automatizado no confirmó la descarga ni pudo repetir la captura usando el token de sesión. Se revisó el caso para comprobar solo el pedido entregado y el enlace de descarga antes y después de recargar; aprobó. La descarga efectiva y la captura repetida se cubrieron manualmente y en pruebas del servidor. En Atlas se comprobó la carga de cinco libros. En PayPal Sandbox se hicieron compras digitales y una impresa con saldo de prueba. La compra digital manual permitió descargar el archivo; la impresa sumó el envío, mostró una guía y redujo el stock de 12 a 11 unidades. El estado «Enviado» apareció en la ventana del cliente sin recargar después de que el personal lo cambió.

La prueba con PayPal reveló un defecto que las pruebas simuladas no detectaron: la captura había terminado en PayPal, pero LibroYa no la había registrado. Se revisó el estado de ambos sistemas antes de crear otro pedido, se corrigió la interpretación de la respuesta y se añadió una opción de conciliación que exige verificar la captura. Esta experiencia mostró que una prueba aprobada con respuestas simuladas no sustituye una comprobación del servicio externo.

Las decisiones manuales fueron elegir el alcance de la tienda, revisar el PRD, configurar Atlas, PayPal Sandbox y Railway, y aprobar los casos de TestSprite después de leer sus pasos. También se separaron las credenciales y las capturas originales del repositorio. La conexión WebSocket pública se comprobó con autenticación, reconexión y recuperación de pedidos. La experiencia dejó un límite concreto: T10 necesita dos sesiones simultáneas para aprobarse dentro de TestSprite, aunque el cambio de estado sí se observó manualmente y se verificó en una prueba de integración.
